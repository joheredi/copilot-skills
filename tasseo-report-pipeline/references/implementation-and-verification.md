# Implementation, publication, and operations

## Before writes

Confirm approval of the exact plan and selected environment. Read live
resources, revisions, ownership/access, active/pending source, publication,
producer/policy state, and relevant schedules. Resolve conflicts before editing.
Preserve user-authored pending work; use isolated candidates when required.

Discover every planned write operation and its completion contract. A generic
tool list is not evidence that producer publication or proposal acceptance is
supported. Establish a checkpoint for each human-only prerequisite.

Capture an operator-owned recovery record outside distributable skill source.
Never persist credentials or raw private transcripts in it.

## Build in dependency order

1. **Data:** verify real field names/values and the analytical population.
   Reuse compatible existing data or execute only approved bounded intake.
   Follow all needed pages and verify terminal completeness.
2. **Facts, if needed:** draft the Measure/Selections against the current
   schemas and calculation contract. Inspect compilation metadata and preview
   real supported inputs. Review compatible versus identity-breaking changes
   and policy migration before activating an exact version.
3. **Presentation:** read the target report before editing; for a new empty
   report, create only after approval, then read it. Inspect datasets,
   `runtime_describe`, and matching gallery examples. Prefer native marks,
   transforms, controls, layout and provenance over emulating legacy HTML.
4. **Reuse, if needed:** author a template with a typed invocation contract.
   Read complete saved source, including continuations, before replacing the
   ordered draft. Preserve block identities and unrelated work. Test-only
   acquisitions must not leak into normal invocation.
5. **Backfill:** execute the approved strategy only after schema/authority/write
   capability gates. Use bounded partitions, track receipts and budget,
   inspect errors and reruns, and verify the historical/future handoff.
6. **Orchestration:** inspect the deployed automation runtime before source
   authoring. Use supported durable calls, explicit inputs and bounded native
   idempotency. Validate, publish and test only within the approved plan.
   Do not accidentally activate a scheduled trigger before prerequisites pass.

These are responsibilities, not a requirement for every task to create six
layers. A missing native dependency is a blocker, not a silent shell fallback.

## Validate effective output

Run the native renderer through MCP with representative parameters and real
approved inputs. Inspect every block's errors/warnings, partial-output metadata,
provenance diagnostics, rendered row/mark counts, labels, units, scale domains,
empty categories and missing values. Follow the native validation ID when a
job is still running rather than enqueueing a different test.

For required exact drill-down, resolve representative **published** marks and
page their contributors. Custom summaries need explicit exact provenance and
stable nested keys. Historical external aggregates without trace members must
show honest lineage/limitations, not misleading interactions.

Run analytical and same-input numerical tests from the plan. For UI-only
changes, compare a same-cycle baseline so a fresh cohort cannot conceal a
semantic regression. A local checker is an independent oracle, not proof that
the native TypeScript renderer ran.

Repair defects and unintended warnings. An intentional noninteractive aggregate
or limitation must match the approved evidence contract and remain disclosed.
Do not hide warnings globally or weaken correctness/identity guards to pass.

## Acceptance and publication

Ordinary report proposals may require operator acceptance. State the exact
validated proposal IDs/revisions and requested action, then re-read active
source and pending state after the operator acts. Revalidate if source or
inputs changed. Template draft writes do not accept ordinary report edits.

For a template, promote the exact tested revision through the supported native
operation. Match invocation parameters and the sample's actual source manifest;
keep test-only data separate. Resume the same promotion run ID if pending.
Instantiation creates a report, not a completed publication.

Where applicable, complete native `report.run` through an approved automation.
Verify completed outcome, saved active source, reader-facing block results,
actual cycle/inputs, provisional flag, caveats and immutable HTML artifact.
Record caveats; block verified delivery if they violate the contract.
Do not call `report_compute`/`report_validate` or template promotion a reader
publication merely because it returned `ok`.

## Verify recurring behavior

- Inspect actual automation version/references, owner and intended trigger.
  Determine pinning and latest-resolution behavior from the live contract.
- Exercise an approved end-to-end API/manual path where supported; inspect its
  durable timeline and downstream publication, not just accepted/queued status.
- Verify schedule timezone, cadence, enabled/paused state, next execution when
  exposed, and any delivery binding. An enabled schedule is not execution proof.
  Report real scheduled execution separately from manually tested equivalence.
- Track data-cycle time independently from calculation/publication, check and
  failed-attempt times. Preserve last-good output when completeness gates fail
  and visibly disclose stale/failure status. Expose unsupported guarantees.
- Use replay-safe retries, bounded late-arrival handling and native corrections.
  Never fabricate a success fact to update freshness.
- Pause only scoped one-time helpers you created after they finish. Do not pause
  the operational pipeline or remove evidence as incidental cleanup.

Do not change delivery audiences, webhook destinations, notifications or source
pipeline activation without plan authority. Source retirement is outside this
read-only migration skill.

## Completion and recovery

For a recurring migration, verified means approved parity checks, actual native
rendering, accepted saved source, completed reader publication and end-to-end
operation, plus verified intended schedule configuration. Scheduled execution
may remain explicitly unobserved. For one-off work, omit irrelevant recurring
requirements; do not omit publication evidence if publication was requested.

When blocked or interrupted, report the furthest proven lifecycle stage and
save environment, roles/IDs, revisions, plan approval, completed/pending
operations, run IDs, evidence locations, remaining budgets and next action.
Re-read state before resuming. After an uncertain write, recover its existing
native job/idempotency identity; do not submit a different operation blindly.
